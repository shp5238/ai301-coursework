# Rubric: is this plan ready to post and build from?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| diagnosis-grounded | Read the candidate plan's diagnosis and proposed fix against the issue context and the repro-evidence block, including controls, logs, and the earliest point where the bad behavior appears. | Pass when the stated cause and chosen change explain the reproduced behavior without contradicting a control or claiming the defect occurs after the evidence shows it already occurred. A plan may describe a narrow causal hypothesis when the evidence cannot prove the exact line, but it must preserve that uncertainty and choose work that can verify it. | required |
| scope-bounded | Read the plan's in-scope and out-of-scope statements, files or components, approach, and plan comment against the issue's requested outcome. | Pass when the work is one bounded change needed for the issue. Related cleanup, migrations, redesigns, new options, broader platform work, or "while here" changes must be excluded unless the package shows they are necessary to produce the requested outcome. | required |
| approach-executable | Read the plan's files or areas, implementation steps, chosen layer, and unresolved decisions against the repo-facts block. | Pass when a contributor unfamiliar with the draft could begin the change without first choosing among major architectures, locating the basic implementation area, or deciding whether the fix belongs upstream, downstream, or in a dependency. Exact line numbers are not required. | required |
| test-observable | Read the test plan against the repro evidence's commands, inputs, failure artifact, and expected behavior. | Pass when the test plan names a command or concrete check that exercises the real changed path and states an observable before/after result that would distinguish the fix from the reproduced failure. A generic full-suite run may supplement but cannot replace a targeted observation. | required |
| thread-direction-followed | Read the candidate plan and plan comment against explicit maintainer direction, prior-art links, ownership claims, and requested experiments in the issue context or thread highlights. | Pass when the proposal follows, directly answers, or explicitly and reasonably distinguishes every applicable maintainer direction; it must not silently pursue a conflicting approach or race known active work. If the thread contains no applicable direction, pass. | required |
| repo-conventions-followed | Read the repo-facts block's issue or contribution requirements, templates, and AI-use policy against the candidate plan comment. | Pass when the comment includes every convention that explicitly applies to issue comments or proposed work, including a required AI-assistance disclosure. All eval packages are treated as AI-assisted; therefore a policy requiring disclosure of any AI use fails when the comment omits it. A silent policy, or one that does not apply to issue comments, imposes no extra requirement. | required |
| uncertainty-honest | Read the plan's risks, unknowns, alternatives, and deviations against the certainty supported by the issue and repro evidence. | Pass when material unknowns are labeled and the plan explains how they will be checked; fail when guesses are presented as established facts or meaningful decisions are hidden. If no material uncertainty remains, a direct bounded plan passes. | preferred |

## Verdict rule

Return `accept` only when every required check passes. Return `reject` when any required check is `fail` or `unclear`. Preferred checks provide feedback but never change the verdict. For every check, `unclear` means the evidence the check names is genuinely absent or cannot be verified; for verdict purposes, `unclear` counts as `fail` on required checks.
