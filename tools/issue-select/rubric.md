# Rubric: is this a good first issue?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| maintainer-alive | In an eval bundle, inspect the capture date, `last 5 default-branch commits`, `maintainer first-response sample`, and maintainer comments in the issue thread. In live mode, inspect the latest five default-branch commits and recently updated issue threads for Owner, Member, or Collaborator activity. Bot-only commits do not establish maintainer life unless the commit shows a bot merging a human PR. | Pass if at least one of these occurred within the 12 months before the bundle capture date (eval) or today (live): a human-authored default-branch commit, a bot merge of a human PR, or a substantive Owner/Member/Collaborator response or decision. Fail if none occurred within 12 months. If dates or actor roles needed to apply the threshold are absent, grade `unclear`. | required |
| repo-in-use | In an eval bundle, inspect `archived`, `last push to any branch`, `latest release`, and `last 5 default-branch commits` in repo facts. In live mode, inspect the archived banner, newest branch activity, releases, and default-branch commit history. | Pass if the repository is not archived and has at least one push, release, or non-bot default-branch commit within the previous 12 months. Fail if it is archived, or if every available qualifying activity date is more than 12 months old. A missing release alone does not fail an otherwise active repository. If the archived state or all qualifying activity dates are absent, grade `unclear`. | required |
| scope-fits-newcomer | Read the complete issue body and comment thread. In eval mode, also use linked-PR history described in the bundle. Look for a single requested outcome, acceptance criteria or observable behavior, tracking checklists, unresolved design debate, maintainer warnings about core internals, abandoned implementation attempts, whether a proposed new feature has maintainer endorsement, and whether the post is a usage question rather than a contribution task. | Pass if the issue asks for one bounded code, test, documentation, or configuration outcome whose completion can be observed, and the thread contains no unresolved design decision. A single outcome may require coordinated changes to multiple files, documentation pages, or tests and still pass when every change directly supports that same outcome. A performance or correctness bug remains one bounded outcome when it names one observable failure and lists several possible causes or implementation approaches; alternatives are not separate deliverables unless the issue requires each independently. Likewise, a report that identifies a single defect class and names several affected rules, cases, or components as examples is one coherent correction rather than an umbrella task, unless each named item has an independent requested outcome. Optional or explicitly lower-priority follow-up work does not fail the check when the required outcome is bounded. Fail if it is an umbrella/tracking issue containing multiple separate outcomes that could be completed and accepted independently; a pure usage/support question; an open-ended feature wish with no settled expected behavior; a new feature proposed without a maintainer filing it or substantively endorsing its requirements; explicitly requires broad architectural or core-internals work; or has unresolved design debate or repeated abandoned attempts showing that one newcomer-sized change is not settled. Multiple files alone do not make an issue an umbrella task. A short maintainer-filed, newcomer-labeled bug report does not fail by itself when it requests a coherent correction. If the requested outcome or discussion needed to determine boundedness is absent, grade `unclear`. | required |
| unclaimed | In an eval bundle, inspect `this issue: assignees`, `linked PRs`, and the full comment thread for current work claims or PR references. In live mode, inspect the Assignees and Development boxes and the thread. Apply the Path Review house rule from `scope.md` in live mode. | In eval mode, pass if there is no assignee, no open linked or referenced implementation PR, and no current credible claim that remains active. Treat a claim comment as inactive when it is at least 12 months old and has no later evidence of ongoing work, open implementation PR, or assignment; it need not be explicitly released. Fail if an assignee, open implementation PR, or current active claim exists. In Path Review live mode, ignore classmates' claim comments as required by `scope.md`, but still fail an assignee or open linked implementation PR. If claim state cannot be determined from the available evidence, grade `unclear`. | required |
| contribution-policy | In an eval bundle, inspect the `contribution policy` line in repo facts. In live mode, inspect `CONTRIBUTING.md`, contributor documentation it links to, dedicated AI-policy files, and required PR-template disclosures. | Pass if the policy is silent about AI-assisted contributions or permits them outright or subject to conditions such as disclosure, human review, understanding, or testing. Fail if the repository explicitly refuses AI-generated code or documentation in a way that prohibits this course's AI-assisted workflow. If the bundle says no policy exists, pass. If a policy is known to exist but the relevant rule is unavailable, grade `unclear`. | required |
| newcomer-signal | Inspect the issue labels, opener's maintainer association, and issue body for a `good first issue` or equivalent label, a maintainer-filed task, named files/components, or explicit acceptance criteria. | Pass if at least one newcomer-friendly signal is present. Otherwise fail. This check never changes accept or reject. | preferred |

## Verdict rule

Accept an issue only if every `required` check passes. Reject it if any
`required` check fails or is `unclear`. A failed or unclear `preferred` check
never changes the verdict; preferred checks only help rank issues that have
already been accepted.

All recency thresholds in eval mode are measured against the bundle's capture
date, not today's date. In live mode they are measured against today's date.
